# 0914-N09-1 상위설계 — 초기 fill 얕음의 근본 원인 분석과 실행 메뉴

상위 배경: loop524 (`0914-N06`) · loop525 (`0914-N08`) 후 남은 후속 항목. 병렬 loop526 (`0914-N07`) 이 outline generator 텔레메트리를 집계 중.

## 문제 정의

### 두 가지 "얕음" 매커니즘

| 클래스 | Model 출력 상태 | 종착점 | 유저 시야 | loop525 의미 |
|---|---|---|---|---|
| **P1 · unparseable** | JSON outline 을 파싱 불가 (트렁케이션·HTML dump·refusal) | `decideTemplateCloneSlotFillTerminal` → seed-fallback (raw seed) | LOOK seed 배너 | loop525 로 Retry dock 이 이제 뜬다 |
| **P2 · shallow parseable** | 파싱 가능하지만 title-only slides 다수 | `slot-fill` → 저장 후 `shouldQueueSparseContentTopUp` → auto sparse-repair | 저장된 얕은 데크 (+ 자동 개선 시도) | (변동 없음, 기존 자동 완화가 작동) |

**본 loop 는 P1 에 집중.** P2 는 이미 자동 sparse-repair 파이프라인 (loop481) 이 존재.

### P1 이 배너로 낙착되는 정확한 조건

`decideTemplateCloneSlotFillTerminal(input)` 파이프라인 (packages/contracts/src/template-clone-fill.ts:1577):

1. `applyTemplateCloneSlotFill(seed, raw)` — 정상 JSON outline → `slot-fill` (banner 없음).
2. `recoverPartialTemplateCloneOutline(raw)` — 손상된 JSON 에서 `"title"` 리터럴만 살려 partial outline → `seed-fallback` (banner 없음, 부분 outline 이 seed 와 다름).
3. `synthesizeTemplateCloneOutlineFromBrief({ userBrief, deckTitle, slideCount })` — 브리프에서 topic 추출 → 결정론적 outline → `seed-fallback` (banner 없음).
4. 위 3개 모두 실패 → `{ kind: 'seed-fallback', html: seed, title: fallbackTitleGuess }` — decision.html === seed → `templateCloneSeedFallbackShouldWarn(seed, seed) === true` → **LOOK seed banner 노출**.

### 3 단계가 실패하는 원인 (loop373 설계 감사)

`synthesizeTemplateCloneOutlineFromBrief` 는 cover 를 다음 중 하나로 요구:
- `deriveDeckCoverTitleFromBrief(brief)` 로 브리프에서 뽑은 topic 문자열.
- `deckTitle` (일반적으로 project.name).

`SYNTH_GENERIC_TITLE_RE` (`/^(?:슬라이드|deck|slides?|presentation|발표\s*자료|untitled|artifact)$/i`) 에 해당하면 후보에서 배제. 후보가 없으면 null.

즉:
- `userBrief` 가 topical 이면 (예: "www.teamver.com 사이트 분석해서...") synth 성공 → 배너 없음.
- `userBrief` 가 없거나 generic ("슬라이드 만들어줘") 이고 `deckTitle` 도 "슬라이드" 이면 → cover 없음 → null → 4단계 raw seed → 배너.

이는 loop373 의 의도적 설계 결정이다:
> "Never invents topical body copy" — 근거 없는 topic 을 만들지 않고 raw seed 를 유지해 유저에게 실패 신호를 명확히 보여준다.

### loop524 (parallel `resolveTemplateCloneRunBrief`) 의 역할

병렬 세션이 loop524 에 추가한 `resolveTemplateCloneRunBrief` 는 재시도/오토컨티뉴 턴에서 `runVisiblePromptRef.current` 가 감사 프롬프트 (`<!--od:auto_continue_incomplete_output-->`, `[FINAL RETRY]`, "슬라이드 채우기에 실패해...") 로 덮이지 않도록 원본 유저 브리프를 보존한다. 이 helper 는 `userBrief` 파라미터의 신뢰도를 높여 3단계 synth 가 성공할 확률을 크게 올린다.

## 기존 완화 감사

이미 코드베이스에 심어진 방어층:

| 완화 | 위치 | 커버리지 |
|---|---|---|
| 파싱 강화 (`stripTemplateCloneOutlineNoise`, balanced JSON walk) | contracts:template-clone-fill | P1-일부 (트렁케이션 · think 태그 · artifact 래퍼) |
| 부분 outline 복구 (`recoverPartialTemplateCloneOutline`) | contracts:template-clone-fill | P1-일부 (title 리터럴만 남은 JSON) |
| Brief → topical outline 합성 (`synthesizeTemplateCloneOutlineFromBrief`) | contracts:template-clone-fill | P1-일부 (브리프 있으면) |
| Sparse-repair auto queue (`shouldQueueSparseContentTopUp`, `buildSparseContentTopUpPrompt`) | apps/web:teamver/slideCountTopUp | P2 전반 |
| Slide-count top-up | 동일 | P2 (짧게 나왔을 때) |
| Thin-prior full rewrite | 동일 | P1-일부 (얇은 scaffold 만 반환한 경우) |
| Sparse/thin/topUp 프롬프트 hard-rule (loop517-522) | contracts:prompts/system + apps/web | 빈 deck-patch · 잘못된 artifact 방어 |
| LOOK seed 배너 + Retry dock 정합 (loop525) | apps/web + runtime | P1 최종 (배너 후 Retry 원클릭) |
| Outline generator 텔레메트리 (loop526) | contracts + apps/web | 관측만 (behavior 무변화) |

**결론**: P1 완화는 이미 상당히 많이 심어져 있다. 남은 실제 배너 케이스는 근본적으로 "MiniMax 가 파싱 불가 출력을 반환 + 유저 브리프가 없거나 generic" 이다.

## 실행 메뉴 (loop526 데이터 후 선택)

loop526 텔레메트리가 실제 데이터를 수집한 뒤 아래 중 필요한 것만 실행:

### Option A — 낮은 위험 · 문서/UX
- **Empty-brief guardrail**: Home Wizard 등에서 브리프가 실질적으로 비어있는 상태를 조기 차단 (전송 전 사용자에게 topic 확인 요구). → 루프529 / N15
- **배너 카피 개선**: 배너에 "이번 요청에 주제가 명확하지 않았습니다. 채팅에 주제를 더 구체적으로 입력해 주세요." 를 상황별로 표시. → 루프536 / N22

### Option B — 중간 위험 · Synth 확장 (loop373 설계 완화)
- `synthesizeTemplateCloneOutlineFromBrief` 에 옵션 `allowGenericCover: boolean` 추가. Clone content-fill 라이브 마감 경로에서만 `true` 로 호출 → generic 브리프에서도 최소 outline 을 만들어 raw seed 회피.
- **주의**: loop373 이 명시적으로 반대한 방향. 데이터로 "raw seed 노출 ≫ generic outline 노출" 이라는 근거가 필요.

### Option C — 높은 위험 · Prompt/모델 튜닝
- MiniMax JSON slot-fill 프롬프트에 few-shot 예시를 추가해 파싱 실패율 감소 유도.
- Temperature / max-tokens 조정.
- 모델 자체를 Claude/GPT 로 라우팅 (BYOK 유연성).
- **주의**: 프롬프트 크기 증가 → 응답 시간 증가 · 비용 증가. Trade-off 명확한 데이터 필요.

### Option D — 관측 · 회로 차단기
- LOOK seed 배너 노출 빈도를 서버측 분석 (`terminalPersistResultKind=skipped-incomplete` + `CLONE_LOOK_SEED_FALLBACK_STATUS_CODE`) 으로 지속 관측.
- 특정 threshold 초과 시 자동 알림 → 팀이 재검토.

## 이번 loop 산출물

**본 loop 는 코드 변경 없이 분석 문서만 남긴다.** 이유:
1. 유저의 특정 버그 (artifact_regression, Retry dock 부재) 는 loop524 · loop525 로 완전 해결.
2. 남은 배너 노출은 loop373 의 의도적 실패-신호 UX (근거 없는 topic 을 만들지 않음).
3. loop526 텔레메트리가 아직 데이터 수집 중. 선제적 코드 변경은 speculative.
4. 병렬 세션이 loop524 에 이미 `resolveTemplateCloneRunBrief` 를 추가해 재시도 시 브리프 신뢰도를 크게 올림.

데이터가 쌓인 뒤 위 실행 메뉴 중 하나로 별도 loop.
