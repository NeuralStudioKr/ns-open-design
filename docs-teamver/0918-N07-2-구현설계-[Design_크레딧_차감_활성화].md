# 0918-N07-2 구현설계 · Design 크레딧 차감 활성화

상위: `0918-N07-1`  
**2026-09-21 재작성. 이 문서가 차감 ON 구현 SSOT.**

Registry `X-Teamver-Access-Key` · `/api/billing/reserve|commit|refund|balance` 는 구현하지 않는다.  
2026-09-18~21 초안의 Registry 드레인은 이력이다. 합산 드레인·0 가드·킬스위치·B2B/M3는 유지하고 **호출 대상만 Main Apps JWT/M2M + TokenService** 로 바꾼다.

## 1. 인증 — 이미 있는 것

```text
[Browser]  →  BFF cookie  →  design-api
                                │  Apps JWT (aud=teamver-design)
                                │     GET /internal/apps/design/bootstrap   (기존)
                                │
[daemon]   →  internal key  →  design-api estimate-reserve
                                │
                                └─ X-Teamver-Internal-Api-Key  →  Main
                                      GET  /internal/apps/design/credits/spendable  (가드)
                                      POST /internal/apps/design/credits/consume    (드레인)
                                      POST /api/apps/auth/exchange|refresh          (기존)
```

| 호출 | 누가 | 인증 | 왜 |
|------|------|------|-----|
| spendable | design-api 가드 | `TEAMVER_INTERNAL_API_KEY` | daemon→design-api에 유저 JWT가 없다. `/api/credits/*`는 플랫폼 HS256. |
| consume | design-api drain | 같은 internal key | tick에 유저 JWT가 없다. |

`TEAMVER_JWT_AUDIENCE` / `TEAMVER_APP_KEY` / `TEAMVER_JWKS_URL` / `TEAMVER_INTERNAL_API_KEY` 는 이미 hosted 기동 필수. 과금 ON이 새 비밀을 요구하지 않는다.

Main 차감 본체는 채팅과 같다.

- 잔액: `TokenService.effective_spendable_balance` (org 풀·할당 포함)
- 차감: 요청 세션에서 `CreditConsumptionPipeline.run` → `credit_balance` + `credit_transaction`

Design은 Main `usage_billing_outbox`에 INSERT 하지 않는다. 합산은 Design outbox가 하고, Main에는 **창·WS당 consume 1회**만 보낸다.

## 4. 핫패스 (차감 없음, 0 가드만)

```text
DISABLED=1        → 가드 없음, 런 진행, ledger only
차감 ON + spendable ≥ 1 → 런 허용. 끝나면 amount_t enqueue
차감 ON + spendable ≤ 0 → 런 거절 + 토스트
차감 ON + 조회 실패     → 런 거절 + 토스트 (공짜 런 금지)
```

전액 reserve 없음. 예상 200T여도 잔액 1이면 시작한다.

```text
성공 + 실측 토큰
  → credit_meter (B2B ratio, M3 512k) 로 amount_t
  → design_billing_outbox upsert pending
  → ledger pending, credits_committed=false
실패·취소·토큰 0·단가 없음
  → outbox 없음
  → 단가 없고 토큰 있으면 ledger meter_failed
```

`POST /api/internal/billing/estimate-reserve` (design-api, daemon M2M):

| 잔액 | 응답 | daemon |
|------|------|--------|
| 킬스위치 | `amount_t:0`, `policy:"billing_disabled"` | 시작 |
| ≥ 1 | `amount_t:0`, `policy:"billing_deferred"` | 예약 없이 시작 |
| ≤ 0 | `amount_t:0`, `policy:"insufficient_balance"` | 런 실패 |
| 조회 실패 | `amount_t:0`, `policy:"balance_unavailable"` | 런 실패 |

금액은 enqueue 때 고정한다. 드레인은 저장된 `amount_t`만 합산한다.

같은 `(workspace_id, run_id)` 는 outbox 한 행. `pending`이면 `amount_t` 갱신. `processing`/`done`은 불변.

### 4.1 잔액 캐시

런마다 Main GET을 치면 핫패스가 다시 무거워진다.

- `spendable>0` 만 WS별 **60초** 기억. 그 사이 GET 생략
- `≤0` 은 캐시하지 않음 (충전 직후 막히지 않게)
- consume이 `insufficient_balance`면 그 WS 캐시 즉시 삭제
- 킬스위치 ON이면 GET 0회

daemon은 JWT를 들지 않는다. design-api가 workspace_id만 받아 Main spendable을 M2M으로 친다.

### 4.2 토스트

| policy | daemon/FE 코드 | KO |
|--------|----------------|-----|
| `insufficient_balance` | `TEAMVER_INSUFFICIENT_BALANCE` | 크레딧이 부족해 이번 작업을 시작할 수 없습니다. |
| `balance_unavailable` | `TEAMVER_BALANCE_UNAVAILABLE` | 크레딧 잔액을 확인할 수 없어 이번 작업을 시작할 수 없습니다. |

## 5. Main API (신규)

경로 prefix는 기존 Apps 내부 API와 같게 `/internal` ( `/api` 아님 ).

### 5.1 `GET /internal/apps/design/credits/spendable`

| | |
|--|--|
| 인증 | `X-Teamver-Internal-Api-Key` (`require_teamver_internal_api_key`) |
| 쿼리 | `workspace_id` 필수 |
| 인가 | path `app_key`는 `design`만. WS가 존재해야 함. 멤버십은 design-api가 런 시작 전에 이미 본 것으로 친다 |

### 5.2 `POST /internal/apps/design/credits/consume`

| | |
|--|--|
| 인증 | `X-Teamver-Internal-Api-Key` 만 |
| body | `workspace_id`, `amount_t` (`ge=1`), `reference_id` (필수, 최대 128), `user_id` 선택 |
| 동작 | 요청 세션에서 `CreditConsumptionPipeline.run`. `consume_after_usage_for_subscriber` 는 새 세션을 열어 락이 깨지므로 쓰지 않는다 |
| 멱등 | `credit_transaction` 에 `(reference_type='design_billing', reference_id)` 가 있으면 **재차감 없이 200** `{status:"already_consumed", spendable_t}` |
| 잔액 부족 | 400 `billing.insufficient_balance`, 차감 없음 |
| 응답 성공 | `{status:"consumed"|"already_consumed", spendable_t}` |

`reference_id` 형식: `design:{workspace_id}:{settlement_id}`. Design이 만들고 Main이 그대로 키로 쓴다.

**전용 테이블 없음.** Design outbox를 Main에 복제하지 않는다.

동시 요청: `pg_advisory_lock(hashtext('design_billing:'||reference_id))` (세션 락) 후 조회·차감. 파이프라인 `rollback()` 이 나도 유지. 응답 전에 unlock.

부분 UNIQUE (채팅 `usage` 행과 싸우지 않음):

```sql
CREATE UNIQUE INDEX uq_credit_transaction_design_billing_ref
  ON credit_transaction (reference_id)
  WHERE reference_type = 'design_billing' AND reference_id IS NOT NULL
```

org_pool 은 `reference_type=usage` / `reference_id=workspace_id` 만 남긴다. consume 서비스가 **같은 TX**에 `design_billing` 행을 보강한다. 성공한 차감을 장부 insert 실패로 롤백하지 않는다.

## 6. Design outbox · 합산 드레인

목적은 핫패스에서 Main consume을 빼고, N개 런을 **창·WS당 consume 1회**로 묶는 것이다.

```text
tick 300초
  → DISABLED? 0건
  → 같은 DB 커넥션에서 pg_try_advisory_lock. 실패면 skip.
    (세션을 반납하면 락이 풀린다. drain이 끝날 때까지 유지. 다른 세션 unlock 금지)
  → stale processing(attempted=false, lock 만료) → pending 복귀
  → 대상 WS 최대 20
  → WS 직렬, 창당 consume 1:
       1) consume_attempted=true 이면 같은 consume_reference_id 로 resume
       2) 아니면 pending(attempted=false) claim → 새 settlement
       3) consume_attempted=true 후 HTTP. claim 세션 없이
       4) 200 → done + ledger committed
  → unlock (락을 잡은 그 세션에서)
```

HTTP 중에 claim 세션을 잡지 않는다. WS 병렬 금지. 인라인 settle 없음.

`POST /api/internal/billing/drain-outbox` 는 같은 로직을 한 번 돌린다. 런 종료마다 호출하지 않는다.

이미 Registry `reserved` 인 옛 장부 행이 있으면 **resume하지 않는다.** Registry를 다시 치면 안 된다. 운영 대조 후 수동. 새 런은 consume 경로만.

### 6.1 테이블 `design_billing_outbox`

`schema_bootstrap` `CREATE TABLE IF NOT EXISTS`.

| 컬럼 | 의미 |
|------|------|
| `id` | PK |
| `workspace_id`, `run_id` | UNIQUE. 런당 1행 |
| `amount_t` | enqueue 시점 크레딧 |
| `status` | `pending` · `processing` · `done` · `failed` · `dead` · `stuck` |
| `settlement_id` | 합산 배치 id. claim 때 |
| `consume_reference_id` | Main에 보낸 `reference_id`. consume 직전 기록해도 됨 |
| `consume_attempted` | HTTP 직전 짧은 TX에서 true |
| `locked_until` | processing 만료. 만료만으로 재consume 하지 않음 |
| `attempts`, `last_error` | |
| `model_name` | 감사 |
| `created_at`, `updated_at` | |

인덱스: `(status, workspace_id)`, UNIQUE `(workspace_id, run_id)`.

`registry_usage_id` / `reserve_attempted` 컬럼을 쓰지 않는다. 이미 만든 테이블이 있으면 rename 또는 새 컬럼 + 구컬럼 무시.

### 6.2 크래시 (consume 1회라 Registry 2단계보다 단순)

Main consume이 `reference_id` 멱등이므로 재시도가 안전하다.

| 상태 | 다음 tick |
|------|-----------|
| processing + `consume_attempted=false` + 응답 없음 | pending 복귀. 재consume 허용 |
| processing + `consume_attempted=true` | **같은 reference_id로 consume 재시도** → 200이면 done. 재시도가 두 번째 차감이 되면 버그(Main 멱등 실패) |
| done 기록 전 크래시, 이미 consumed | 재호출 `already_consumed` → done |
| consume 400 insufficient | `failed`, attempts+1. **같은 reference_id 유지**. pending+새 settlement 금지. 5회 `dead`. 가드 캐시 무효 |
| consume 5xx/timeout | `failed`, 같은 reference_id 로 재시도. 5회 `dead`. **환불 API 없음** |
| 배치에 reference_id가 섞임 | `stuck`. 추가 consume 금지 |

Registry 때 쓰던 “reserve 후 usage_id 없으면 stuck, 재reserve 금지”는 폐기한다. 두 단계가 없어졌다.

## 10. 검증 (구현 시)

- DISABLED=1: enqueue 0, drain 0, spendable/consume 0, 가드 없음
- ON + 0: estimate insufficient, 토스트, outbox 없음
- ON + GET 실패: unavailable, 토스트
- ON + ≥1: deferred, 런 허용. N런 1 WS → consume 1
- 같은 reference_id consume 2회 → Main 차감 1
- consume_attempted 후 재진입 → 재차감 0, done
- session spy: HTTP 동안 checkout 0
- 겹친 tick skip
- 201번째 pending → 이번 200 + 다음 1
- DISABLED 전환 후 과거 장부 소급 0
- Registry 라우트 테스트 추가 없음. Design 단위 테스트가 Registry를 mock하면 JWT/M2M mock으로 교체
