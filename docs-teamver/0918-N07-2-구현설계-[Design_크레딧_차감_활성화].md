## 3. 데이터 흐름 (ON) — 폐기, §7로 대체

아래는 2026-09-18 당시 설계다. **차감을 켜는 경로는 §7 드레인으로 바꾼다.** 런 시작 예약·런 종료 즉시 commit 은 구현하지 않는다.

```text
managed:
  run start → estimate-reserve (prices or flat) → Registry reserve
  run end success → commit(usage_id)
  run fail → refund(usage_id)
  병행: usage/events ledger upsert

BYOK:
  message terminal PUT → finalize-byok-run
    meter(tokens) → reserve(amount_t) → commit → ledger billing_status
```

## 7. 후속 슬라이스 — 드레인(outbox) 차감

상태: **설계 확정, 구현 전.** 이 절이 차감 ON 의 SSOT 다. §3 은 이력만 남긴다.

기준: Main BE `usage_billing_outbox_service.consume_after_usage_with_outbox` 의 **ENABLED + CONSUME** 모드. 요청 경로에서는 금액을 기록만 하고, 워커가 나중에 잔액을 줄인다. Design 은 `TokenService` 를 직접 호출하지 않으므로, 워커의 차감 수단은 기존 Registry `reserve` → `commit` 이다.

### 7.1 하지 않는 것

| 항목 | 이유 |
|------|------|
| 런마다 즉시 reserve/commit | 사용자가 거부한 방식. §3 |
| Main BE `usage_billing_outbox` 테이블에 Design 이 직접 INSERT | 구독자·org 풀은 Main 소유. Design 은 Registry 경계만 넘는다 |
| `TEAMVER_BILLING_DISABLED=1` 인 동안 outbox 에 넣기 | 나중에 스위치를 켜면 기록만 하던 과거 런이 한꺼번에 차감된다 |
| 과거 장부 재계산·소급 차감 | 차감이 한 번도 켜진 적 없다 |
| 차감 스위치 기본값 변경 | staging 은 `DISABLED=1` 유지. 이 설계의 구현만으로 잔액은 변하지 않는다 |
| Shadow(enqueue 와 동시에 inline consume) | Main 의 이행용 모드. Design 은 드레인만 둔다 |

### 7.2 스위치

| 상태 | 동작 |
|------|------|
| `TEAMVER_BILLING_DISABLED=1` (지금 staging) | 장부에 토큰·`credits_amount_t` 만 기록. `billing_status=disabled`. outbox 없음. Registry 없음. 드레인 tick 은 0건 |
| 스위치 OFF + Registry 키 있음 | 성공 런만 outbox `pending`. 잔액은 드레인 tick 에서만 감소 |
| 스위치 OFF + Registry 키 없음 | enqueue 는 하되 드레인은 `registry_not_configured` 로 행을 `pending` 에 남긴다. 런은 막지 않는다 |

별도 `TEAMVER_BILLING_ENABLED` 는 만들지 않는다.

### 7.3 핫 패스 (차감 없음, 0 가드만)

성공한 런이 끝난 뒤에만 금액을 확정한다. 런 시작에 예산을 잡아 두지 않는다. **쓸 잔액이 0이면 시작만 거절한다** (§7.13).

```text
managed / BYOK 공통:
  시작: 잔액 ≥ 1 인지 확인 (전액 reserve 없음). 0·조회실패면 거절
  런 수행 (시작 시 Registry reserve 없음)
  성공 + 실측 토큰
    → credit_meter (B2B ratio, M3 512k 포함) 로 amount_t
    → design_billing_outbox upsert (pending)
    → ledger billing_status=pending, credits_committed=false
  실패·취소·토큰 0·단가 없음
    → outbox 없음
    → 단가 없고 토큰은 있으면 ledger meter_failed (기존 fail-closed 유지)
```

`POST /api/internal/billing/estimate-reserve` 는 차감 ON 이어도 예약 금액은 0 이다 (`policy:"billing_deferred"`). 대신 **쓸 수 있는 잔액이 1 미만이면 런을 시작하지 않는다** (§7.13). 예산 전액 reserve 는 하지 않는다.

금액은 enqueue 시점에 고정한다. 드레인은 저장된 `amount_t` 만 Registry 에 넘기고 다시 단가를 계산하지 않는다. B2B 여부·512k 구간은 그때의 `plan_id` 와 토큰으로 이미 반영돼 있다.

같은 `(workspace_id, run_id)` 로 usage 이벤트와 BYOK finalize 가 둘 다 와도 outbox 는 한 행이다. `pending` 이고 아직 `registry_usage_id` 가 없으면 `amount_t` 를 최신 실측으로 갱신한다. `processing` / `done` 이면 금액을 바꾸지 않는다.

### 7.4 드레인 — 워크스페이스 합산

목적은 **핫패스에서 Registry 를 빼는 것**과 **N개 런을 1번의 reserve+commit 으로 묶는 것**이다. 런마다 늦게라도 reserve 하면 호출 수는 즉시 차감과 같다.

```text
tick (기본 300초)
  → [짧은 TX] pg_try_advisory_lock('design_billing_drain') 실패면 skip
  → pending workspace 최대 20개 (커넥션 즉시 반납)
  → 워크스페이스 하나씩 직렬:
       [짧은 TX] pending → processing + settlement_id, reserve_attempted=false
       [짧은 TX] 같은 settlement_id 에 reserve_attempted=true
       세션 없이 HTTP reserve(합)
       [짧은 TX] registry_usage_id 기록
       세션 없이 HTTP commit
       [짧은 TX] settlement_id → done + ledger committed
  → advisory unlock
```

Registry HTTP 중에는 DB 세션을 잡지 않는다 (§7.11). 한 tick 에서 워크스페이스 병렬 처리 금지.

킬스위치 ON 이면 tick·수동 drain 모두 0건. `POST /api/internal/billing/drain-outbox` 는 같은 합산 로직을 즉시 한 번 돌린다(운영 재처리용).

이미 `reserved` 인 예전 장부 행은 기존 resume-commit 을 유지한다. 새 성공 런은 그 경로로 보내지 않는다.

### 7.5 테이블 `design_billing_outbox`

`schema_bootstrap` 에 `CREATE TABLE IF NOT EXISTS`.

| 컬럼 | 의미 |
|------|------|
| `id` | PK |
| `workspace_id`, `run_id` | UNIQUE. 런당 기록 1행. 차감은 워크스페이스 합산 |

인덱스: `(status, workspace_id)`, UNIQUE `(workspace_id, run_id)`.

### 7.7 검토에서 정한 것

| 질문 | 결정 |
|------|------|
| plan 캐시 60초가 요금제를 지우나 | 아니다. 60초는 `workspace_billing_plans` 재조회 간격이다. 차감 금액은 enqueue 때 고정. 드레인 tick 은 300초 |
| 잔액이 0 이면 런을 막을까 | **막는다** (§7.13). 1 이상이면 시작. 시작 후 합산이 잔액을 넘으면 그 배치는 `failed`/`dead` |
| 관리형 런의 예산(3.2만/8천)으로 차감하나 | 하지 않는다. 실측 토큰의 `amount_t` 만 드레인한다. §3 의 과다 예약 차감은 사라진다 |
| usage 와 BYOK 가 둘 다 넣으면 | UNIQUE 한 행. pending 이고 예약 전이면 금액만 갱신 |
| 드레인 도중 프로세스가 죽으면 | §7.12. usage_id 있으면 commit 만. reserve_attempted 없고 usage_id 없으면 pending 복귀. reserve_attempted 있고 usage_id 없으면 stuck |
| 스위치 ON 인 기록만 하던 행 | outbox 에 없으므로 드레인 대상이 아니다 |

### 7.8 검증 (구현 시)

- 킬스위치 ON: enqueue 0, drain 0, Registry 호출 0, **잔액 GET 0**, ledger `disabled`
- 차감 ON + spendable 0: estimate `insufficient_balance`, 런 없음, outbox 없음
- 차감 ON + spendable ≥ 1: estimate `billing_deferred`, 런 허용
- 차감 ON + 잔액 GET 실패: `balance_unavailable`, 런 없음
- spendable>0 캐시 60초 안: 두 번째 런은 GET 생략
- 드레인 `insufficient_balance` 후 같은 WS 런: 캐시 무효, GET 후 거절
- 킬스위치 OFF: 성공 런 N개 → outbox pending N행, Registry 0. drain 1회(같은 WS) → reserve 1 + commit 1 → 전부 `done`
- 같은 배치 drain 두 번 → Registry reserve 는 한 번
- reserve 실패(잔액 부족 등 4xx) → `failed`, commit 없음. 다음 tick 재시도 후 5회 `dead`
- commit 이 예약이 아직 있다고 거절 → refund 후 `failed`
- commit 타임아웃/5xx → **환불하지 않음.** usage_id 유지한 채 `stuck` (이미 빠졌을 수 있음)
- 실패 런 → outbox 행 없음
- 기존 `reserved` 장부 행 → resume-commit 유지 (새 런은 이 경로 아님)

### 7.9 검토 재점검 (2026-09-21, 부하 목적 재정렬)

이 절이 이 슬라이스의 최종 판단이다. 앞절과 충돌하면 이 절을 우선.

**15초 + 인라인 settle 은 즉시 차감과 같다.** 호출 수(Registry reserve/commit, Main consume)가 런 수와 1:1이다. 핫패스만 비동기로 옮긴 것이고, 서버 부하는 줄지 않는다. 드레인을 쓰는 이유가 부하면 그 설계는 틀린다.

비교:

| 방식 | 핫패스 | Registry 호출 | 잔액 반영 | 부하 |
|------|--------|----------------|-----------|------|
| 런마다 즉시 reserve+commit | 막힘 | 런당 2회 | 즉시 | 기준 |
| 런마다 outbox + 15초/인라인 | 안 막힘 | 런당 2회 (조금 뒤) | ~즉시 | **절감 없음** |
| 런마다 outbox + 5분 tick | 안 막힘 | 런당 2회 (늦게) | 최대 5분 | 첨두만 분산, **총량은 동일** |
| **WS 합산 + 5분 tick** | 안 막힘 | **창·WS당 2회** | 최대 5분 | **총량 감소** |

더 짧은 tick 은 잔액을 빨리 맞출 뿐, 호출을 줄이지 않는다. 더 좋은 방법은 합산이다.

**설계 문제점 — 합산 기준으로 처리한다.**

| 문제 | 조치 |
|------|------|
| 2 EC2 노드가 같은 pending 을 잡을 수 있다 | WS 단위 원자 claim: `UPDATE … SET status='processing' WHERE workspace_id=? AND status='pending' RETURNING *`. 한 노드만 그 WS 합산을 한다 |
| 크래시가 reserve 직후, `registry_usage_id` 저장 전에 발생 | `reserve_attempted=true` 이면 `stuck`. 재 reserve 금지. 잔액은 아직 안 빠졌을 수 있음. 운영 대조 |
| 크래시가 commit 직후, `done` 저장 전 발생 → 재드레인이 commit 을 또 호출 | Registry `commit` 은 `reservation_not_found` 를 던진다. 기존 `_is_reservation_not_found` 판정으로 `already_finalized` 처리 후 `done`. **완화 있음** |
| 잔액 부족으로 reserve 실패 | 런은 이미 성공했다. 되돌리지 않는다. `failed` + `last_error='insufficient_balance'` + attempts 증가. 5회 뒤 `dead`. **다음 런부터는 §7.13 가드가 막는다** (드레인 실패 시 캐시 무효) |
| Registry 장기 다운 → `pending` 이 계속 쌓임 | attempts 5 도달 후 `dead`. `dead` 는 재시도하지 않는다. 남은 tick 은 최신 pending 만 |
| 하나의 run 에 usage 이벤트와 BYOK finalize 가 모두 도착 | `(workspace_id, run_id)` UNIQUE + `ON CONFLICT DO UPDATE`. pending 인 동안 amount_t 갱신 허용. `processing/done/failed/dead` 이면 그대로 |
| 런 시작 시점의 plan_id 와 드레인 시점의 plan_id 가 다르면 | enqueue 순간에 amount_t 를 고정한다. 드레인은 그 값만 사용. 워크스페이스가 그 사이 요금제를 바꿔도 이미 계산된 금액으로 청구 |
| ledger 와 outbox 순서 뒤집힘 | enqueue 는 ledger 업서트와 **같은 DB 트랜잭션**. 트랜잭션이 커밋된 뒤에만 Registry 호출을 한다. 트랜잭션 outbox 패턴 |
| kill switch 를 껐다가 다시 켰을 때 | pending/processing 은 tick 에서 skip. 이미 `done` 인 행은 그대로. 재시도가 필요하면 스위치를 다시 켜야 한다 |

**Main BE 수정 — 잔액 읽기만.**

- Registry `/reserve /commit /refund` 산식은 그대로.
- **추가:** `GET /api/billing/balance?workspace_id=` → `{spendable_t}` (`effective_spendable_balance`). 쓰기는 없다. reserve(1) 프로브 금지.
- Design 이 Main 의 `usage_billing_outbox` 를 건드리지 않는다.
- 잔액 차감은 기존 `registry_billing_commit` → consume 파이프라인.

**Main 에 남기고 싶은 후속 (별도 슬라이스, 지금 하지 않음)**

| 항목 | 이유 |
|------|------|
| Registry `reserve` 에 idempotency key 헤더 지원 | 지금은 크래시가 reserve 직후에 발생하면 재드레인이 안전하게 재실행할 수 없다. Main 이 `Idempotency-Key: {workspace_id}:{run_id}:{attempt}` 를 받아 같은 키의 예약을 반환해 주면 `stuck` 를 없앨 수 있다 |
| Registry `commit` 에 amount 오버라이드 허용 | 지금은 reserved 금액 그대로 확정. Design 은 이미 실측 금액을 넣으므로 이번엔 필요 없음 |
| `usage_billing_outbox` 스타일 스토어 프로시저 공용화 | Design 이 자체 outbox 를 두므로 이번엔 미필요 |

### 7.10 확정 — 합산 드레인 (인라인 없음)

| 스위치 | 기본 | 이유 |
|--------|------|------|
| `DESIGN_BILLING_OUTBOX_DRAIN_TICK_SEC` | **300** (5분) | 창 안에 런이 모일수록 합산 이득. 15·60초는 거의 즉시 차감 |
| `DESIGN_BILLING_OUTBOX_DRAIN_WORKSPACE_LIMIT` | 20 | tick 당 처리할 WS 수 |
| `DESIGN_BILLING_OUTBOX_DRAIN_RUNS_PER_WS` | 200 | 한 WS 합산에 넣을 최대 pending 행 |
| `DESIGN_BILLING_OUTBOX_INLINE_SETTLE` | **0** | 켜면 부하 절감이 사라짐. 구현하지 않음 |
| `DESIGN_BILLING_OUTBOX_LOCK_TTL_SEC` | 60 | 합산 reserve+commit 여유 |
| `DESIGN_BILLING_OUTBOX_MAX_ATTEMPTS` | 5 | 도달 시 `dead` |

잔액 UI 는 최대 약 5분 늦을 수 있다. 그것이 이 방식의 비용이다. 창을 줄이면 부하 이득도 줄어든다.

운영이 창을 비우고 싶으면 `POST /drain-outbox` 한 번이면 된다. 런 종료마다 돌리지 않는다.

### 7.11 위험 대비 (구현 계약)

구현이 이 절과 어긋나면 버그다. 코드보다 이 절이 우선이다.

#### 부하

| 위험 | 대비 |
|------|------|
| 런마다 Registry | 합산 1회. 인라인 settle 없음 |
| tick 이 이전 tick 과 겹침 | 프로세스 가드. 이전이 끝나지 않으면 이번은 skip. 로그 `drain_overlap_skipped` |
| 20 WS 를 동시에 HTTP | **직렬**. 동시 Registry 1개 |
| 수동 drain + tick 동시 | 같은 claim. 후순위는 0행 |
| 핫패스가 무거워짐 | enqueue 는 INSERT/UPSERT 한 번. 시작 가드는 `spendable>0` 60초 캐시 + GET. 전액 reserve 없음 |

#### DB 세션 풀

상용 워커당 pool 10+overflow 10. 세션을 HTTP 에 묶으면 풀이 먼저 탄다.

| 금지 | 이유 |
|------|------|
| `async with session` 안에서 `reserve`/`commit` | 왕복 수 초~타임아웃 동안 checkout 유지 |
| 워크스페이스 N개를 gather 로 병렬 | checkout × N |
| drain 이 `psycopg` 동기 연결을 추가로 염 | `workspace_plan` 과 다른 풀. drain 은 금액 재계산을 하지 않으므로 호출 금지 |
| claim 트랜잭션을 HTTP 끝까지 유지 | idle-in-transaction + 풀 고갈 |

허용된 세션 수명: **claim / usage_id 기록 / done·ledger 각각 수 십 ms 짜리 짧은 TX**. HTTP 전후에 `session.close`. tick 전체에서 동시에 checkout 되는 세션은 최대 1.

Registry 타임아웃은 기존 billing timeout(기본 5초). 실패해도 세션은 이미 반납된 상태여야 한다.

#### DB 꼬임

| 위험 | 대비 |
|------|------|
| 장부만 있고 outbox 없음 | 성공 런의 ledger upsert 와 outbox upsert 를 **같은 커밋**. 한쪽만 커밋 금지 |
| outbox 만 있고 장부 없음 | 같은 트랜잭션. 실패 시 둘 다 롤백 |
| claim 중에 같은 run 이 금액을 바꿈 | `ON CONFLICT` 는 `status='pending' AND registry_usage_id IS NULL` 일 때만 `amount_t` 갱신. processing/done 은 불변 |
| claim 이후 도착한 새 런 | 새 pending 행. 이번 합산에 안 넣고 다음 창 |
| 배치 일부만 done | `UPDATE … WHERE settlement_id=?` 한 문장. 행 루프 커밋 금지 |
| 장부 `billing_status` 가 usage 후속 이벤트로 덮임 | `done`/`committed` 는 usage upsert 가 되돌리지 않음. `pending` 도 `disabled`/`not_attempted` 로 강등 금지 |
| 한 배치에 `registry_usage_id` 가 서로 다름 | 데이터 손상. 그 배치는 `stuck`, 추가 reserve 금지, 메트릭 `billing_outbox_inconsistent` |

#### 중복 기록·중복 차감

중복 차감이 가장 비싼 실패다. reserve 가 잔액을 잠그지 않으므로, **같은 배치를 두 번 commit 하면 두 번 빠진다.**

| 경로 | 대비 |
|------|------|
| usage + BYOK 가 같은 run | UNIQUE `(workspace_id, run_id)`. 행 하나 |
| 두 노드가 같은 WS | `UPDATE … WHERE status='pending' RETURNING`. 패배 노드는 0행 |
| claim 후 크래시, usage_id 없음 | `stuck`. **재 reserve 금지**. 과소 청구는 있어도 이중 청구는 없음 |
| usage_id 기록 후 크래시, commit 전 | 다음 tick 은 reserve 없이 commit 만. `already_finalized` 면 done |
| commit 성공 후 done 기록 전 크래시 | 재 commit → `reservation_not_found` → done. consume 은 한 번 |
| 배치에 usage_id 가 섞임 | stuck. 새 reserve 금지 |
| 킬스위치 OFF 직후 과거 장부 | 과거 행은 outbox 없음. reconcile 은 **스위치가 켜진 뒤에 생긴** 성공 런만 재적재 (`used_at` ≥ 스위치 켜진 시각 또는 outbox 테이블 생성 이후). 소급 차감 금지 |

#### 누락

| 경로 | 대비 |
|------|------|
| enqueue 트랜잭션 실패 | 장부도 롤백. daemon 재보고 시 다시 upsert |
| 200행 상한에 잘림 | 남은 행은 pending. 다음 tick. 유실 아님 |
| 20 WS 상한에 잘림 | 다음 tick. 유실 아님 |
| reserve 전 크래시 (이미 processing) | `reserve_attempted=false` 이고 usage_id 없음 → pending 복귀. 재 reserve 해도 이중 차감 아님 |
| reserve 성공·usage_id 미기록 크래시 | `reserve_attempted=true` → stuck. 재 reserve 금지. 잔액은 보통 아직 안 빠짐. 운영이 Registry 예약과 대조 |
| 일시 Registry 오류 | `failed`, attempts+1, **다음 tick 에 pending 복귀** (usage_id 없을 때). 5회면 `dead` |
| 잔액 부족 | 런은 유지. 다음 tick 재시도 후 `dead`. 메트릭 `billing_outbox_dead` |
| 성공 장부인데 outbox 행이 없음 | reconcile 은 **outbox 행이 없을 때만** pending 삽입. outbox 가 done/processing/stuck 인데 장부만 늦으면 장부만 맞춤. **새 reserve 금지** |
| `dead`/`stuck` | 자동 재처리 없음. 알림 후 수동 |

#### tick 수명

```text
1. DISABLED? → 0건
2. [짧은 TX] advisory lock 실패 → skip (다른 워커/노드가 이미 드레인 중)
3. 짧은 TX: pending WS id 최대 20
4. 각 WS 직렬, §7.4
5. 짧은 TX: reconcile — outbox 없는 성공 장부만 최대 50행
6. advisory unlock
```

예외가 나도 unlock 은 한다. HTTP 예외는 해당 settlement 만 failed/stuck 로 닫고 다음 WS 로 간다.

워커가 여러 개여도 tick 루프는 떠 있을 수 있다. **실제 작업은 advisory lock 승자 하나만.** 프로세스 메모리 가드만으로는 부족하다.

#### 관측

로그/메트릭 (기존 `teamver_usage_5xx` 계열):

- `billing_drain_tick` processed_ws, runs, reserved_amount, duration_ms
- `billing_outbox_stuck` / `dead` / `inconsistent` 건수
- `billing_drain_overlap_skipped`
- drain 전후 pool `checked_out` — drain 중 2 이상이면 세션 누수

#### 구현 시 테스트

- 같은 run usage+BYOK → outbox 1행
- 두 코루틴이 같은 WS claim → 승자 1
- claim 후 usage_id 없이 재진입 → reserve 0, stuck 또는 pending 복귀 규칙대로
- usage_id 있는 processing 재진입 → commit 만
- commit already_finalized → done, consume mock 1회
- session spy: reserve/commit await 동안 checkout 0
- 겹친 tick → 두 번째 skip
- 201번째 pending → 이번 200 + 다음 1
- reconcile 이 committed 행을 다시 넣지 않음
- DISABLED=1 에서 enqueue 0·reconcile 0
- processing + reserve_attempted=false + usage_id 없음 → pending 복귀, reserve 재시도 허용
- processing + reserve_attempted=true + usage_id 없음 → stuck, reserve 0
- outbox done + 장부 pending → reconcile 이 reserve 하지 않고 장부만 committed
- commit timeout → refund 0, stuck
- 잔액 0 → estimate insufficient_balance, enqueue 0
- 잔액 GET 실패 → balance_unavailable, enqueue 0
- spendable>0 캐시 TTL 안 → Main GET 0회
- 드레인 insufficient 후 캐시 무효 → 다음 런 GET

### 7.12 최종 검토에서 고친 것 (2026-09-21)

문서 앞절이 서로 다르게 적혀 있던 부분을 여기서 닫는다.

| 구멍 | 왜 위험한가 | 확정 |
|------|-------------|------|
| processing + usage_id 없음 을 무조건 pending 복귀 | reserve HTTP 직후 크래시면 재예약 → **이중 차감** | `reserve_attempted` 라벨. false 만 복귀 |
| 같은 상태를 무조건 stuck | reserve 전에 죽어도 영구 누락 | 위와 같음. 라벨 없으면 구분 불가 |
| reconcile 이 장부만 보고 재삽입 | outbox 는 이미 done 인데 장부 갱신만 실패한 경우 **다시 reserve** | outbox 행이 없을 때만 insert. 있으면 장부 동기화만 |
| commit 실패 시 무조건 refund | 타임아웃이면 이미 consume 됐을 수 있음. 환불하면 잔액이 늘어남 | 명확한 “아직 reserved” 거절만 refund. 5xx/timeout 은 stuck |
| 워커당 drain task | uvicorn 워커 × EC2 대수만큼 tick. claim 은 막아도 DB/락 소음 | `pg_try_advisory_lock` 한 승자만 본문 수행 |
| 20 WS × 타임아웃 5초 × 2 | tick 하나가 최대 ~200초. 다음 300초 tick 과 겹치면 skip → 대기 최대 ~10분 | 허용. 상한을 늘리면 풀·Registry 부하가 다시 커짐 |
| 상위 N07-1 이 런 시작 거절·즉시 commit | 구현자가 구 경로를 살림 | ON 동작은 이 문서 §7. N07-1 은 이력+킬스위치 |
| Main 예약이 잔액을 잠그지 않음 | 다른 WS 가 같은 org 풀을 동시에 commit 하면 과지출 가능 | Main 기존 동작. Design 은 WS 직렬만 보장. 0 가드는 시작만 막음 |
| 잔액이 최대 5분(밀리면 ~10분) 늦음 | 기획: 채팅은 즉시 차감에 가깝다 | 차감 반영은 지연. **잔액 0 에서 새 런만** 즉시 막음 (§7.13) |
| Main `credit_transaction` 은 창·WS 당 1줄 | 런별 내역은 Design 장부 | 관리자 화면이 Main 만 보면 런 단위가 안 보임. 의도 |

기획으로 아직 안 여는 것: Priority 1.5×, 5분보다 짧은 잔액 반영, 예상 금액만큼 선예약.

### 7.13 잔액 0 이면 런 금지

차감 ON 일 때 **쓸 수 있는 크레딧이 1 미만이면 런을 시작하지 않는다.** 1 이상이면 예상 금액과 비교하지 않고 시작한다. 전액 reserve 로 되돌리지 않는다.

```text
DISABLED=1        → 가드 없음
차감 ON + 잔액 ≥ 1 → 런 허용, 끝나면 outbox
차감 ON + 잔액 ≤ 0 → 런 거절 (managed·BYOK 시작 모두)
차감 ON + 잔액 조회 실패 → 거절 (잔액 증명이 없으면 공짜 런 금지)
```

**잔액 정의:** Main `TokenService.effective_spendable_balance` (org 풀·할당 포함). 워크스페이스 raw `credit_balance` 만 보면 org 풀 WS 가 0으로 막힌다.

**Main 추가 (작음):** Registry 키로 `GET /api/billing/balance?workspace_id=`. 응답 `{spendable_t:int}`. 쓰기는 없음. 지금 Registry 에 잔액 조회가 없어 reserve(1) 프로브는 쓰지 않는다(예약 쓰레기·이중 호출).

**Design:** `POST /api/internal/billing/estimate-reserve` 가 워크스페이스를 받아 잔액을 본다.

| 잔액 | 응답 | daemon |
|------|------|--------|
| ≤ 0 | `amount_t:0`, `policy:"insufficient_balance"` | 런 실패 |
| ≥ 1 | `amount_t:0`, `policy:"billing_deferred"` | 예약 없이 시작 |
| 조회 실패 | `amount_t:0`, `policy:"balance_unavailable"` | 런 실패 (`estimateUnavailable`) |

**부하:** 런마다 Main GET 을 치면 핫패스가 다시 무거워진다.

- 워크스페이스별 `spendable>0` 만 **60초** 기억. 그 사이 GET 생략
- `spendable≤0` 은 기억하지 않고 매번 확인 (충전 직후 막히지 않게)
- 드레인이 `insufficient_balance` 이면 그 WS 캐시를 즉시 0 으로 지움 → 다음 런은 GET
- 킬스위치 ON 이면 GET 0회

**하지 않는 것:** 예상 토큰만큼 막아 두기, 잔액 1 인데 예상 200T 라고 거절하기. 그건 다시 즉시 차감/선예약이다. 0 가드만 한다.
