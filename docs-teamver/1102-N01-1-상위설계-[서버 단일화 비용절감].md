## 1. 배경 / 목표

### 1.1 배경

코드·Terraform·운영 문서는 **Design EC2 2대 + ALB(Active-Active)** 를 전제한다.

- 커밋된 tfvars: **staging·prod 모두 `ec2_instance_count = 2`**.
- affinity SSOT는 ALB cookie가 아니라 **nginx `hash` (userId / projectId)** ([39_2](./39_2_ALB_nginx_라우팅_설계.md) · [39_6](./39_6_라우팅_아키텍처_CTO_의사결정.md)).
- ALB stickiness는 **이미 OFF** (`alb_stickiness_enabled = false`).
- 2대는 **용량 2× + 1대 장애 시 서비스 지속** 용. 상용 1호기의 필수 조건은 아니었다 ([39_0 §3.1](./39_0_Design_이중화_로드맵_개요.md) — 단일 `t3.2xlarge`로 오픈 가능).

비용을 줄이기 위해 **서버는 1대만 유지**한다. 본 문서는 그 전환에 **필요한 변화 목록**이다. **구현은 사용자 검토 후.**

### 1.2 목표

| 목표 | 내용 |
|------|------|
| 인스턴스 | Design **EC2 1대** (staging / prod 각각 — 적용 범위는 사용자 확인) |
| 비용 | 2번째 EC2 + 전용 EBS + 2번째 EIP 제거. ALB는 **유지 권장**(아래 §5) |
| 안전 | scratch/SQLite split-brain 위험 **소멸** (writer 1). 배포는 단일 호스트 `deploy.sh` |
| 코드 | **검토 전 변경 금지.** 불필요 코드는 이후 구현설계에서 선택 삭제 |
| 제품 | fillMode · EMPTY · 슬라이드 게이트 · Main 앱 로직 **불변** |

### 1.3 이 문서가 다루지 않는 스택 (혼동 방지)

| 스택 | 오늘 이중화? | 본 문서 |
|------|--------------|---------|
| **Design staging / prod** (`teamver-design`) | **tfvars 2대.** 운영 runbook에 node2 IP/ID 존재 | **대상** |
| **Main Staging** (`stg` / `stg-api`, CICD `43.201.164.51`) | **1대** (`teamver-staging` `enable_ec2` count 고정 1, EIP 기존 유지) | 비대상 — 이미 단일 |
| **Main Production** (GCP `teamver.com` / `api.teamver.com`) | GCP LB + API VM 풀(문서상 2~3대) + ANALYSIS 1대 + Memorystore | **비대상.** 별도 비용 논의 |
| **teamver-page** EC2 ×2 | API + AI worker **역할 분리** (이중화 아님) | 비대상 |
| **Mail** | 1대 | 비대상 |

MemKraft(`이중화` / `sticky` / `staging 서버`)에는 Design 이중화 엔티티가 거의 없고, CICD 호스트(`43.201.164.51`) live-note만 있다. 본 조사의 SSOT는 39 시리즈 + Terraform tfvars.

**라이브 AWS 조회(2026-11-02):** 이 환경의 AWS 자격 증명이 유효하지 않아 DescribeInstances 실패. **실제 running 대수·2번째 공인 IP는 apply 전 `terraform output` / AWS 콘솔로 재확인 필수.** 커밋된 `output.txt` / `output-prod.txt` 는 **1노드 시절 스냅샷**(ALB·`ec2_public_ips` 배열 없음)이라 tfvars와 불일치한다.

## 2. 현행 (이중화 전제)

### 2.1 Staging vs Production — Design

| 항목 | Staging (커밋 tfvars) | Production (커밋 tfvars) |
|------|----------------------|--------------------------|
| Terraform | `staging.terraform.tfvars` | `prod.terraform.tfvars` + `backend-prod.hcl` |
| `ec2_instance_count` | **2** | **2** |
| 인스턴스 | `t3.large`, root 50GiB, od-data 30GiB **× 대수** | `t3.2xlarge`, root 100GiB, od-data 100GiB **× 대수** |
| ALB | `enable_alb = true`, ACM `e6852de4-…` | `enable_alb = true`, ACM `5b3a1673-…` |
| Sticky | **OFF** (nginx hash) | **OFF** (nginx hash) |
| Deregistration delay | 300s (SSE drain) | 300s |
| EIP | `enable_ec2_eip = true` → **대수만큼** (SSH) | 동일. 사용자 DNS는 ALB |
| 공개 80/443 on EC2 | `[]` (ALB SG만 :80) | `[]` |
| DNS (GCP) | `stg-design.teamver.com` · `stg-design-api.teamver.com` → **ALB CNAME 의도** | `design.teamver.com` · `design-api.teamver.com` → **ALB alias** |
| Main BE | `https://stg-api.teamver.com` | `https://api.teamver.com` |
| RDS | 공유 `teamver-staging-postgres` / DB `teamver_design_staging` | 전용 `teamver-design-prod-postgres` **Multi-AZ** (EC2와 별개 — **유지**) |
| S3 | `teamver-design-staging-data` | `teamver-design-prod-data` |
| ASG | **없음.** `count = var.ec2_instance_count` | 없음 |

[31](./31_Design_Staging_vs_Production_네트워크_TLS_DNS.md) 는 staging을 「EIP + certbot, `enable_alb=false`」로 적는다. **현재 커밋 tfvars는 staging도 ALB ON.** 31은 구버전으로 보고, **운영 진실은 tfvars + 39_4 D1~D6.**

### 2.3 트래픽 경로 (현행 2대)

```text
Browser
  │ HTTPS
  ▼
ALB (TLS, round-robin, stickiness OFF, idle 3600s)
  ├─ EC2-1 nginx :80
  └─ EC2-2 nginx :80
        │ auth_request → design-api session-probe → userId
        │ hash(userId | projectId) → peer :7456
        ▼
  선택된 노드의 open-design-daemon
        scratch / app.sqlite (노드 로컬) / S3 SSOT
```

- `/_nginx/health`, static, `/teamver-bff/*` → **로컬** (ALB RR OK).
- `/api/*` → **hashed upstream** (`teamver-design-od-daemon-upstream.inc.conf` + `peers.inc`).
- peer 목록: `render_od_daemon_peers_nginx.sh` 가 같은 `Service=teamver-design` + Env 태그 EC2 **전부**를 넣음. 127.0.0.1 을 hash ring에 넣지 않음.
- daemon publish: 2노드면 `OD_DOCKER_PUBLISH_HOST=0.0.0.0`, SG self **7456**.
- `OD_NODE_ID` = IMDS instance-id → health `nodeId` · `X-OD-Node-Id` · `X-Design-Api-Node`.
- Litestream: `litestream/<node-id>/app.sqlite` 노드별 prefix.

### 2.4 배포

| 방식 | 내용 |
|------|------|
| 단일 호스트 | 각 EC2에서 `bash deploy.sh --staging|--production --rds` |
| 2노드 | Mac/CI에서 `rolling_deploy.sh` — **순차** drain → SSH deploy → local health → register. 병렬 아님. `--hosts "u@ip1 u@ip2"` |
| git | rolling이 pull 하지 않음. **사전 동일 SHA** 필수 (아니면 ChunkLoadError, [31 §8.2.1](./31_Design_Staging_vs_Production_네트워크_TLS_DNS.md)) |
| 롤백 | 남은 healthy target 1대 유지. `ec2_instance_count=1` + deregister 도 문서화됨 |

### 2.5 앱이 2대를 전제하는 이유 (깨지는 것)

daemon은 **stateless가 아니다.** scratch · SQLite · in-memory BYOK cap · in-memory BFF refresh coalesce 가 **노드 로컬**. 2대에서 round-robin만 하면 split-brain · 502 · [39_10](./39_10_HA_세션쿠키_경합_해결.md) 쿠키 경합 · [0807-N01](./0807-N01-1-상위설계-[prod%20cold-node%20PROJECT_NOT_FOUND%20hotfix].md) cold-node 404. 그래서 hash + peers + rolling이 필요했다.

**쿼럼 / “2대 모두 healthy” 강제 코드는 없음.** ALB는 target 1대만 healthy여도 서비스한다. 하드코딩된 2번째 공인 IP도 앱 코드에는 없고 runbook 예시에만 있다.

## 3. 단일화 시 필요 변화

코드 삭제는 **선택**. 인프라 count=1 만으로도 서비스는 1대 경로로 동작한다(peers가 산 노드 1개만 가리키면). 아래는 **안전하게 1대만 남기기 위한 필수/권장**.

### 3.1 변화 표

| 영역 | 해야 할 일 | 우선 | 비고 |
|------|------------|------|------|
| **인프라** | `ec2_instance_count = 1` (해당 env tfvars) | **필수** | 2번째 `aws_instance` / EBS / EIP / TG attachment destroy. `moved` 블록은 `[0]` 유지 |
| **인프라** | apply 전 **어느 인덱스가 남을지** 확인 | **필수** | 기본은 `[0]`(node1) 유지. node2를 남기려면 state mv 필요 — 권장하지 않음 |
| **인프라** | node2 od-data 스냅샷(선택) 후 destroy | 권장 | S3가 파일 SSOT. sqlite는 Litestream prefix |
| **인프라** | ALB **유지** (권장) 또는 EIP 직행 | 결정 필요 | §5. sticky는 이미 OFF → 추가 작업 없음 |
| **인프라** | `alb_deregistration_delay=300` 유지 가능 | 임의 | 단일 타겟이면 drain 의미 축소. 비용 거의 없음 |
| **인프라** | SG `:7456` self ingress | 자동 | `count > 1` 일 때만 생성 → 1이면 사라짐 |
| **인프라** | Prod RDS Multi-AZ · S3 · ACM | **유지** | EC2 이중화와 무관 |
| **인프라** | ASG 도입/제거 | 없음 | ASG 없음 |
| **DNS** | ALB 유지 시 CNAME 불변 | — | EIP 직행 시에만 GCP A 레코드 변경 |
| **배포** | `rolling_deploy.sh --hosts` 를 **1 host** 또는 그냥 `deploy.sh` | **필수(운영)** | 2 host 리스트를 그대로 쓰면 2번째에서 실패 |
| **배포** | 각 노드 `git pull` 동기화 절차 단순화 | 권장 | 1대면 ChunkLoadError 교차 원인 소멸 |
| **배포** | `render_od_daemon_peers_nginx.sh` 재실행 | **필수(전환 직후)** | 죽은 peer IP가 hash ring에 남으면 502 |
| **배포** | `OD_DOCKER_PUBLISH_HOST` | 권장 `127.0.0.1` | 1대면 peer 불필요. 0.0.0.0 남겨도 동작하나 노출면만 줄임 |
| **BE (design-api)** | `suppress_session_cookie` (39_10) | **유지** | 단일 노드에서도 올바른 동작. 지우면 회귀 위험 |
| **BE (design-api)** | `TEAMVER_DESIGN_NODE_ID` / `X-Design-Api-Node` | 유지(무해) | 관측용. 삭제 불필요 |
| **daemon** | `OD_NODE_ID` / `X-OD-Node-Id` | 유지(무해) | |
| **daemon** | Litestream per-node prefix | **유지** | 1대여도 prefix 유지가 restore에 유리 |
| **daemon** | in-memory BYOK cap · scratch | **유지** | 단일 writer. cap은 노드 로컬이 맞음 |
| **nginx** | hash upstream + peers.inc | 단순화 **선택** | 1대면 hash ring 멤버 1개 = 사실상 local. 당장 안 지워도 됨 |
| **FE embed** | API/WS base URL · cookie domain | **변경 없음** | 호스트명 동일 (`stg-design*` / `design*`) |
| **FE Main / admin** | `NEXT_PUBLIC_API_URL` 등 | **변경 없음** | Design 이중화와 무관 |
| **관찰** | `UnHealthyHostCount` 알람 임계 (min healthy 2 가정 시) | 확인 | 1대면 0=장애. 알람 문구만 수정 |
| **관찰** | 두 노드 `X-OD-Node-Id` 교차 검증 | 폐기 | 단일 노드 고정값 |
| **문서** | 39_4 「현재 Production Phase 0 — 1 EC2」와 tfvars=2 불일치 해소 | 구현 후 | 본 전환이 Phase 0 복귀임을 명시 |
| **문서** | 31 staging=EIP 서술 vs tfvars ALB | 구현 후 | |
| **문서** | devops `01_teamver_서버_구성_개요.md` (2026-06, 1대+EIP) | 구현 후 | |

### 3.2 2대가 사라지면 깨질 수 있는 것 (전환 실수)

| 위험 | 조건 | 완화 |
|------|------|------|
| nginx 502 / 잘못된 daemon | `peers.inc` 에 죽은 private IP 잔존 | count=1 apply **직후** 남은 노드에서 render + nginx reload |
| rolling 실패 | 운영자가 예전 `--hosts` 2개 복사 | runbook 1 host로 교체 |
| 잘못된 노드 destroy | Terraform이 `[1]`이 아니라 `[0]`을 지움 | plan에서 instance-id 대조. node1(`54.116…` / `3.34…`) 유지가 기본 |
| DNS 장애 | ALB를 같이 끄면서 CNAME을 안 바꿈 | ALB는 1차에서 **끄지 말 것** |
| sqlite 유실 | node2만 최신 scratch였는데 destroy | 전환 직전 활성 트래픽을 node1로 drain; S3 sync-up 확인 |

### 3.3 불필요해지는 것 (지워도 되는 후보 — 코드 단계에서)

- ALB stickiness 블록을 켜는 운영 (이미 OFF).
- 2 host rolling 예시·ProxyJump node2.
- `OD_DOCKER_PUBLISH_HOST=0.0.0.0` 기본값 (staging/prod `.env.example` 주석).
- 2노드 ChunkLoadError / cold-node / sticky 검증 시나리오(39_5 A5 등) — **문서만**.
- **지우면 안 되는 것:** §4.

## 4. 그대로 두어야 할 것 vs 지우면 안 되는 것

### 4.1 반드시 유지

| 항목 | 이유 |
|------|------|
| S3 project-data SSOT + sync-down/up | 단일 노드여도 디스크 장애 복구 |
| Litestream (및 restore 리허설) | sqlite 백업. prefix 유지 |
| od-data **전용 EBS** (공유 금지 원칙) | 나중에 다시 2대 올려도 split-brain 방지 |
| `deploy.sh` 단일 호스트 경로 | 1대 운영의 SSOT |
| 39_10 `suppress_session_cookie` / 쿠키명 격리 | 워커 다수·재배포 시에도 유효 |
| design-api RDS (staging 공유 / prod 전용 Multi-AZ) | BFF SSOT. EC2 1대와 무관 |
| Main BE JWT / session-probe / cookie domain | 인증 계약 |
| `OD_BYOK_PROXY_MAX_PER_WORKSPACE` 등 **단일 노드 cap** | OOM 방지. 「전역 cap을 노드 간 합산」 로직은 원래 없음 |
| Health `/_nginx/health` · `/api/health` · `/healthz` | ALB·운영 |
| SSE timeout (ALB 3600 / nginx 3600) | BYOK stream |
| Prod ACM + (권장) ALB | TLS |

### 4.2 유지해도 무해 (삭제 급하지 않음)

- `OD_NODE_ID` 헤더/필드, node-id 미들웨어·테스트.
- `ec2_instance_count` 변수 자체 (default 1, 1~4). **tfvars만 1**.
- `rolling_deploy.sh` (호스트 1개로도 동작).
- hash upstream + 1줄 peers.inc.

## 6. 권장 순서

**코드보다 인프라. 코드는 본 문서 검토 후.**

```text
0. 사용자 결정: staging만? prod도? ALB 유지?
1. 라이브 확인: terraform output + AWS (instance-id, TG health, DNS)
2. (선택) node2 drain — ALB deregister, 트래픽을 node1로
3. peers.inc 를 node1만 남기고 nginx reload  ← 2대 중 1대만 살릴 때 502 방지
4. tfvars `ec2_instance_count = 1` → plan (destroy = node2 + vol + eip + attachment만)
5. apply
6. 남은 1대: deploy.sh 또는 기존 compose 유지 + health
   curl https://<design-host>/_nginx/health
7. 문서 갱신 (39_4 「현재 1 EC2」, 31, devops 01) — 구현현황 1102-N01-3
8. (이후, 선택) 코드/스크립트 정리 — 구현설계 1102-N01-2
```

| 순서 원칙 | 이유 |
|-----------|------|
| **staging 먼저** | 39 시리즈 원래 게이트. prod t3.2xlarge 실수 비용이 큼 |
| **인프라 count=1 먼저** | 앱은 1대에서도 이미 동작하게 작성됨 (default count=1, hash ring 1멤버) |
| **ALB 1차 유지** | DNS/TLS 변경을 이중화 롤백과 분리 |
| **코드 나중** | 사용자 검토. 급히 지우면 39_10·nodeId 테스트만 깨짐 |
| **Main BE/CICD 손대지 않음** | 이미 단일(staging) 또는 별 스택(prod GCP) |

ALB를 나중에 내릴 때(선택 2차):

1. EC2 `ec2_public_web_cidr_blocks` 에 80/443 개방 + nginx https/certbot (staging 구패턴).
2. GCP DNS: CNAME/ALB → A/EIP.
3. `enable_alb = false` apply.
4. **prod는 ALB 유지 강력 권장** (31의 원래 설계).
