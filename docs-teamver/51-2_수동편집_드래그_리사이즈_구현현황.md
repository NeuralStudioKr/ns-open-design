## 상세 기록 — flow 카드 move sibling reflow 방지 (2026-08-04)

### 배경

수동 편집에서 카드 3개가 한 줄로 배치된 구간의 첫 번째 카드만 선택해 이동했는데, 형제 카드까지 같이 움직이거나 전체 카드 조합이 재배치되는 것처럼 보이는 문제가 보고됐다. 이 케이스는 카드가 `flex`/`grid`/normal flow 안에 있고, 선택 대상은 `static` 또는 `relative` flow item인 경우에 주로 발생한다.

### 원인

이전 move 정책은 flow 요소를 드래그하면 `position:absolute`로 승격하고 width/height/margin을 고정했다. DOM parent는 유지하지만 요소가 normal flow에서 빠지므로, parent layout engine이 즉시 남은 형제들의 위치를 다시 계산한다. 따라서 형제 요소의 style을 직접 바꾸지 않았더라도 사용자 화면에서는 “선택하지 않은 카드도 이동했다”처럼 보인다.

### 결정

flow item move는 자유 배치로 완전히 빼내는 것보다, 원래 layout slot을 유지하는 것이 더 안전하다고 판단했다. 이에 따라 static/relative flow 요소는 `position:relative` + `left/top` offset으로 이동한다. 이렇게 하면 선택 요소의 DOM 위치와 레이아웃 슬롯이 유지되어 형제 카드 reflow가 생기지 않는다.

### 적용 범위

| 대상 | 동작 |
|------|------|
| `position:static` / `relative` 텍스트·링크·카드 | `position:relative` + `left/top` offset |
| `position:absolute` / `fixed` | 기존 anchored move 유지 |
| flow image/SVG | resize-in-place 유지, move 승격 금지 |
| `position:sticky` | move 비활성. sticky inset/scrollport CB 혼합으로 전용 UX 전까지 제외 |

### 구현 포인트

- static/relative `promoteMoveStyles`는 `position:relative` offset만 쓴다 (size/margin lock 없음).
- sticky move는 `canPromoteTarget`에서 제외한다. 저수준 helper의 sticky absolute 경로는 기존 fixture/분석용으로 남기되 UI에서는 호출하지 않는다.
- flow(static/relative) 시작 좌표는 authored relative offset(`left/top`, 없으면 0).
- 패널 POSITION Left/Top은 absolute/fixed/**relative**에 노출 (static/sticky는 힌트).
- FileViewer optimistic target은 commit된 `position` 값을 반영한다.

### 검증

- `move-math` / overlay / bridge / ManualEditPanel vitest.
- Playwright: static relative promote · resize undo · nested absolute (시드 fixture).

### 잔여 리스크

relative offset은 원래 슬롯을 유지하므로, 사용자가 카드를 큰 거리로 이동하면 원래 자리의 빈 공간이 남을 수 있다. 이 동작은 “선택하지 않은 형제 요소가 재배치되는 문제”를 막기 위한 의도적 선택이다. 향후 그룹 단위 레이아웃 편집이 필요하면 별도 group/container edit UX로 분리해야 한다.

## 상세 기록 — move/resize pointerdown 직후 박스 튐 방지 (2026-08-04)

### 배경

이전 보강 후에도 드래그를 시작하는 순간, 또는 첫 `pointermove`가 threshold를 넘기 전 parent가 scale/paint를 다시 측정하면 선택 박스가 잠깐 다른 위치로 튀는 현상이 남아 있었다. 사용자는 요소를 아직 이동하지 않았는데 박스가 순간적으로 이전 위치나 엉뚱한 paintRect로 보이는 문제다.

### 원인

overlay는 idle 상태에서 실제 DOM 측정값인 `hostPaintRect`를 우선 사용한다. 그런데 `pointerdown` 직후에는 아직 `liveViewportPos`가 없어 gesture 중임에도 idle 규칙이 한 프레임 적용될 수 있었다. 이때 FileViewer가 stale `hostPaintRect`나 변경된 `previewScale`/`hostOffset`으로 rerender하면, 드래그 좌표계가 얼기 전의 측정값이 overlay 표시를 덮어 박스가 튄다.

### 수정

resize와 move 모두 `begin*` 시점에 `liveViewportPos`를 현재 target rect로 즉시 세팅한다. 첫 preview 전부터 display source가 gesture 좌표계로 고정되므로, parent의 stale paint/scale rerender가 overlay 위치를 이기지 못한다. 실제 pointer delta 변환은 기존처럼 pointerdown 때 freeze한 `drag.hostScale`만 사용한다.

### 추가 결정

sticky 요소는 `canPromoteTarget`에서 다시 제외했다. sticky의 `left/top`은 normal relative offset이 아니라 sticky inset이고, absolute promotion은 scrollport containing block에 의존한다. 이 경로는 드래그 중 스크롤/paint 측정 race에 취약하므로, sticky 전용 move UX를 만들기 전까지는 안전하게 비활성화한다.

### 검증

- move pointerdown 후 stale `hostPaintRect` rerender에도 overlay 위치/크기가 유지되는 회귀 테스트 추가.
- resize pointerdown 후 stale `hostPaintRect` rerender에도 overlay 위치/크기가 유지되는 회귀 테스트 추가.
- sticky가 UI promote 대상에서 제외되는 `move-math` 테스트 갱신.
- `move-math` / `resize-math` / `bridge` / `ManualEditResizeOverlay` vitest 통과.
